# T3 持久化重做 — 决策与上下文

> 本文档是 T3（持久化）的决策锚点。实现前必读；回退会话后先读本文档 + 根 `Progress.md` 恢复上下文。
> 状态：`设计已定稿，未开发`。实现时如偏离本文档，回写本文档。

## 0. 一句话

把主 App 的会话持久化从「ChatTurn 平列表 + 回合终态全量替换」重做为「OKIA 树消息级增量落盘 + Room 树形存储 + open(restore) 恢复」，同时修复两个已知 bug（错误回合最后一条不恢复、切会话不持久化）。**不改 OKIA 库**。

## 1. 背景：我们为什么做这次重做

Nexus 的 LLM 运行时已从 `libs:kai` 切到 `libs:okia`（T1-T2c 完成）。主 App 的会话持久化仍是 KAI 时代的形态，靠 `LLMController.getHistory()`（OKIA 树 → ChatTurn 投影）+ `ConversationRepo.saveHistory()`（全量替换 Room）桥接。T3 移除桥接，按 OKIA 的树模型重做存储。

**产品北极星（用户原话）**："我们的用户心智是偏聊天对话的"。所有持久化决策都以此为准——不是 CLI 编码 agent 的会话，是聊天 app 的对话历史。

## 2. 三个外部参照（已调研 codex/pi/fx，2026-08-22）

| 仓库 | 持久化时机 | 错误回合处理 | 对我们的取舍 |
|---|---|---|---|
| pi | 第一条 assistant 消息才落盘（此前仅内存） | **无回复回合不落盘**，崩溃即丢 | 否决（理由见 §3-D3） |
| codex | 流式逐条写 JSONL + SQLite 增量投影 | `StoredTurnStatus=Failed` + ErrorEvent 后 break，注释 "let the user continue the conversation" | 采纳语义：错误后会话可继续 |
| fx | 回合完成时提交；回合中途仅崩溃检查点 | `InterruptedTerminalReason=failed` 作为一等历史形态 | 参考 |

pi 的 SQLite `entries` 表（`session_id, seq, id, parent_id, type, timestamp, payload`）与 OKIA `ConversationEntry`（id/parentId/timestamp/message）几乎同构——佐证我们的数据结构选择是主流做法。

## 3. 核心决策

每条格式：**决策 → 为什么 → 意味着什么（实现影响）**。

### D3-1 持久化粒度 = 消息级（不是块级、不是定时）

- **为什么**：OKIA 的 commit 粒度天然是消息级——`onCommit` 只在整条消息（`Assistant` = thinking/text/toolCall 块组合）完整产出时触发，流式中途的半条是 `live` 不 commit。块级没有干净触发点（ThinkingEnded/TextEnded 自己攒块拼历史会与树不一致，复杂度暴涨）；定时是伪需求（消息级已保证"每条产出即落盘"，定时器徒增协程与时序复杂度）。
- **live 的维度澄清**（易误解点）：`live: AssistantMessage?` 是**一整条**正在流式的消息（内部才是 `List<ContentBlock>`），不是单块。崩溃丢 = 最后一条未 commit 的消息（可能含多个块），不是"最后一个块"。
- **用户定性（原话）**："这对我来说就像写日记，写到一半合上本子，再打开"——崩溃丢"最后一句没说完"可接受，用户重说即可。
- **意味着**：持久化触发点 = 观察 OKIA `conversation: StateFlow<Conversation>` 的 history 变化（每次 onCommit 发射一次），不是回合终态。

### D3-2 Room 增量 insert，废弃全量替换

- **为什么**：消息级持久化若沿用 `replaceTurnsAndMetadata` 全量替换，每条消息都全量重写，写放大。
- **意味着**：`saveHistory` 改为「只插 `turn_index` 大于现有 MAX 的行」。水位 = Room 现有最大 turn_index，无需额外状态字段。

### D3-3 数据结构 = conversation_entry 树形 + conversation.leaf_id

- **结构**：
  - `conversation_entry(id, parent_id, timestamp, message_json)`——message_json = OKIA `Message` @Serializable
  - `conversation` 表加 `leaf_id` 列
- **为什么树形**：为将来的"左右箭头"（同会话内分支切换）留口子，零改表。当前树是线性（无 rewind 消费者），但 parent_id 必须存。
- **意味着**：Room 推倒重来（D1 已定不写迁移），`ChatTurnJsonCodec` 删除，`ConversationTurnEntity` 改造为 `ConversationEntryEntity`。会话元信息（title/createdAt/draft）留在 conversation 表。

### D3-4 错误回合保留：User + partial 落盘；错误卡片零持久化

- **为什么（用户原话）**："不保留有一个问题，就是如果第一轮就出错，下次回复就会是空的对话历史"；"无法继续的语义是，这个 turn 在执行过程中遇到了必须中断的错误……而不是说这整个对话历史就作废了"。
- **意味着**：
  - OKIA 失败时 `commitPartial` 已把半条 assistant 放进树（§8.16 #8），消息级持久化**自然包含**，零额外代码。
  - 错误卡片（`HomeChatBlock.Error`，`applyError` 加的纯 UI 态）**从不进 history** → 冷启动恢复天然不显示错误，无需任何持久化逻辑（这是选"不存 failed 标记"的原因：存了反而要维护"新消息后清除"）。

### D3-5 不加自动重试；停在报错处等用户下一轮

- **为什么（用户原话）**："我更倾向于直接停在那里显示报错，然后等用户自己打字发起下一轮"。聊天心智：错误是回合级中断，不是对话作废。对齐 codex "let the user continue"。
- **意味着**：T3 不做自动重试。错误可重试维度进 UI 文案（RateLimit/Overloaded/Transport 可重试 vs Auth/Quota 不可重试）是 T4。

### D3-6 不做压缩

- 用户明确：不考虑上下文压缩。数据结构不留 compaction 口子（fx 的 `/compact` 不采纳）。

### D3-7 不改 OKIA

- **为什么**：`conversation: StateFlow<Conversation>` 本来就是消息级发射（onCommit 每条发射一次，RealConversation 同一 Mutex 下原子追加）——高频持久化触发点现成就有。OKIA 哲学就是"树 = 事实，存储位置 host 决定"（PRD §5.3/5.8），落盘方式是 host 自管。`export()/open(restore)` 只是整包快照辅助接口（恢复/归档），与逐条增量共存不冲突。
- **意味着**：持久化 = app 层观察 StateFlow + 写 Room，纯 host 侧实现。**时序无忧**（用户判断）：数据源确定、发射顺序确定（单协程 Mutex 下原子追加）、观察端单协程 collect 按序处理，Room 写是 suspend 事务天然串行。**不加锁/队列**（YAGNI，真出现并发写再补）。

### D3-8 外部接口重构：删 ChatTurn 桥接

- **删**：`LLMController.getHistory()`（全量投影）、`replaceHistory()`（ChatTurn → 重建实例）——这两个是 O1-A 过渡桥接，T3 移除时机。
- **保留**：`resetConversation()` 不删（D3-8 修正，2026-08-22 对齐 A）：它无参、不涉 ChatTurn，内含 `PyRuntime.kill()` + `TerminalSessionPool.closeAll()` + `obtainSession(restore=null, forceNew=true)`——开空会话前清工具资源（避免新会话继承上个回合工具状态），这个动作不能丢；它本来就是"开空会话"的合法入口。**新增**：`newSession()` 或直接复用 resetConversation 返回新树 id（供 Room 会话创建对齐 id）。
- **新增**：
  1. LLMController 暴露 OKIA `conversation: StateFlow<Conversation>`（或包装快照）给 app 观察 → 消息级增量写 Room
  2. `open(restore)` 恢复入口（Room 读 entries → 组装 SessionSnapshot → 重建实例），替代 replaceHistory；`conversationFlow: StateFlow<Conversation?>`（当前会话快照流，实例切换重发射，供持久化器观察）
- **意味着**：`HomeChatState` 持久化从「回合终态轮询全量」（`persistCurrentHistoryIfAny`）改「常驻观察 StateFlow 增量写」。UI 侧 `ConversationFormatter.toHomeTurns` 重写为消费 OKIA `Message`（不再消费 `ChatTurn`）。

### D3-9 切会话/新对话先 stop 再关实例（bug 修复）

- **背景（已确认的 bug）**：`loadConversation`（HomeChatState:479-494）和 `startNewConversation`（:615-621）只 `streamJob?.cancel()` + `replaceHistory`/`resetConversation`，**不 stop、不 persist**。而 `stopGenerating`（:283-288）和 `applyEvent.Completed`（:374）都 persist。两个触发路径：
  1. 丢数据：错误回合后切走/新对话，最后一条不落盘（与冷启动 bug 同源）
  2. 时序：`replaceHistory → obtainSession(forceNew) → okia.close()`——`streamJob.cancel()` 后 OKIA send 协程未清理完时，**close 在活跃回合抛异常**（OKIA §8.7 #5 契约）
- **修复**：切会话/新对话前先 `stop()`（终止回合 + 统一 persist）再关实例。消息级增量落地后"丢数据"路径自动消失（已 commit 消息实时在 Room），只剩时序要理顺。

### D3-10 fork/regenerate = 复制新会话（互不影响）

- **为什么（用户原话）**："fork 出来的东西应该互不影响，这意味着以后发生编辑修改之类的情况也不应该相互造成影响。regen 我暂时也当成 fork 吧"。
- **意味着**：Room 层复制 entries 到新会话（复用现有 `forkConversation` 截断复制），regen = fork + 自动 resend 同一 query。**D4 的"截断子树 + open(restore)"已定**：截断点必须是 User 消息；fork 前无活跃回合（export 活跃回合抛异常）。

### D3-11 对话命名：Fork · / Regenerate · 原标题，落盘 Room

- **为什么**：regen/fork 产生的会话在对话列表是独立条目，命名应可区分。"Fork/Branch" 是合理的产品词，**不需要本地化翻译**（就叫 fork/regenerate，英文单词）。
- **意味着**：
  - fork 时 `title = "Fork · " + 原标题`，regen 时 `title = "Regenerate · " + 原标题`，`titleEdited = true`，**一次写入 Room**，不按状态位在 UI 动态渲染。
  - **多语言 XML 仍要落地**（用户要求）：各语言文件都写英文值（如 `fork_title = "Fork · %1$s"`），未来真要翻译时改值即可。
  - fork 出的新会话树 id 与 Room id 的对应关系：待 T3 排期时定（倾向新 Room id = 新 OKIA 树 id）。

### D3-12 清理 `stopCurrentRound(keepCurrentTurn)` 参数

- 该参数恒为 true（OKIA 停止不动会话树，下一轮自然承接历史），T4 清理为无参。T3 顺带或 T4 都行。

## 5. 验收标准

**单测**：
1. 存储往返：save → getConversation 全量一致（id/parentId/timestamp/message 逐字段）
2. bug 回归：错误回合（Failed）后 persist → 冷启动 restore → 最后一条 User 存在
3. 切会话：错误回合后 loadConversation(其他) → 原会话 Room 含最后一条
4. fork/regenerate：Room 截断 entries → D4 子树 → open(restore) 后 history 与截断点一致；leafId 往返
5. Formatter：OKIA 树（User/Assistant 含 ToolCall/ToolResult 配对/Thinking 忽略）→ HomeChatTurn 渲染正确
6. 桥接删除：LLMController 无 getHistory/replaceHistory 残留；app 无 `com.niki914.kai` import（编译期保证）

**手动**：真机 → 触发"当前无法继续"（断网/改错 endpoint）→ 杀进程 → 冷启动 → **最后一条 User 仍在**，可继续对话。正常对话重启恢复、fork、regenerate 各一轮。

**命令**：`:app:testDebugUnitTest` + `:agent-runtime:testDebugUnitTest` 全绿；`grep -r "com.niki914.kai" app/src agent-runtime/src` 为空。
